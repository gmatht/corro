ZORK_WALKTHROUGH — corro 0.7.0 on the zork backend
========================================================================

Every transcript below is VERBATIM output of the real binary, captured by
piping commands into it. Nothing here is summarised, paraphrased, or
reconstructed. Where a line says "You selected", a corro menu action really
fired; the last section shows the one case where that is provable from the
outside.

Regenerate any section with:

    cargo build --no-default-features --features zork
    printf 'light\ngo 68\nnorth\ngo 5\nselect 9\nquit\n' | ./target/debug/corro

To play it yourself:

    cargo run --no-default-features --features zork

The backend is corro's real GUI path -- window, formula row, canvas with its
draw callback, scrolled viewport, menu model -- built against an in-memory
widget tree instead of a display. The REPL is the "display": you walk the
tree, and menu items dispatch the same `SimpleAction` callbacks the GTK menu
would.

Note on the `>` prompt: the REPL reads via `rustyline`, which does not echo a
prompt when stdin is a pipe. Interactive sessions do show `> `.

3. THE WIDGET TREE IS THE DUNGEON — walking it
------------------------------------------------------------------------

The menus are not a child of the window directly. corro builds the bar into
the outer layout box, so the route from the window is "go 68" (the box) and
then "north":

    $ printf 'light\ngo 68\nnorth\n' | ./target/debug/corro
    You are in a vertical Box.

    To the west: SimpleAction
    To the north: Menu Bar
    To the south: Window "corro 0.7.0"

    $ printf 'light\ngo 68\nnorth\n' | ./target/debug/corro
    You are at the Menu Bar.
    Menu items:
      1. _File
      2. _Edit
      3. _Insert
      4. Fo_rmat
      5. _Sheet
      6. _Help

The six items are corro's six top-level menus, in corro's own order, with the
underscores where corro's accelerator mnemonics are -- `_File` (Alt+F),
`E_xit`, `S_ave as`. Those underscores came from corro's menu construction, not
from this document.

`east` / `north` / `south` move through the tree: north is a child, south is the
parent, east is the next sibling. It is the widget hierarchy, traversed.

Every direction names its destination. Before the menus were labelled this
read "To the north: Menu" for all twenty of them, which is not a direction, it
is a coin flip.

5. FIRING A MENU ACTION -- `select` dispatches the corro callback
------------------------------------------------------------------------

    $ printf 'light\ngo 68\nnorth\ngo 8\nlook\n' | ./target/debug/corro
    You are at the Format Menu.
    Items:
      1. _Scope
      2. _Number
      3. _Align
      4. _Reset
      5. _Night mode

    To the west: Insert Menu
    To the east: Sheet Menu
    To the north: Scope Menu
    To the south: Menu Bar

`go <n>` from the menu bar walks the bar's surroundings; the six top-level
menus are `go 5` through `go 10`, in corro's own order:

    bar go 5  -> You move to File Menu.
    bar go 6  -> You move to Edit Menu.
    bar go 7  -> You move to Insert Menu.
    bar go 8  -> You move to Format Menu.
    bar go 9  -> You move to Sheet Menu.
    bar go 10 -> You move to Help Menu.

    $ printf 'light\ngo 68\nnorth\ngo 8\nselect 5\n' | ./target/debug/corro
    You selected "_Night mode".

`select 5` is not just a print. It calls `ZorkState::menu_select`, which
looks up the item's action name (`app.toggle_night_mode`) and calls
`activate_action` -> `click(id)`, which runs the callbacks corro registered
on that `SimpleAction`. Same dispatch path the GTK menu bar uses.

6. WHAT `select` DOES AND DOES NOT PROVE
------------------------------------------------------------------------

That the callback *runs* is covered by a test, because a REPL session gives
you no way to observe it:

    $ cargo test -p rswidgets --no-default-features --features zork menu_select

    running 2 tests
    test backends::zork::model::tests::menu_select_refuses_separator ... ok
    test backends::zork::model::tests::menu_select_dispatches_named_action ... ok

`menu_select_dispatches_named_action` registers a `Cell<bool>` on the action
node, selects the item, and asserts the flag flipped.

**What this does NOT show:** that a selected item changed anything you can
see. It does not. corro's menu actions talk to the app -- they set a status
string, mutate the document, quit the event loop -- and the zork REPL prints
only the model, so no app-level effect is observable from inside a session.
`select` returning a label is therefore not by itself evidence that a real
corro feature ran.

Concretely, the obvious demonstration does not work, and it is worth being
explicit because it is the thing one would naturally reach for:

    $ printf 'light\ngo 68\nnorth\ngo 5\nselect 9\nlight\n' | ./target/debug/corro
    ...
    You selected "E_xit".

`E_xit` is corro's real quit action, so selecting it looks like it should
end the session. It does not. `app.quit` calls `rxapp.quit()`
(`src/gui/menu.rs:228`), which sets a flag on the GUI event loop, and the
zork REPL never reads that flag -- it loops on `ZorkState::running` instead.
The `light` typed *after* the selection still runs, and `Goodbye!` is printed
only when `quit` is typed explicitly, not at EOF. Both halves verified by
counting, with and without the selection:

    $ printf 'light\ngo 68\nnorth\ngo 5\nselect 9\nlight\n' \
        | ./target/debug/corro | grep -c "You light the lantern"
    1
    $ printf 'light\ngo 68\nnorth\ngo 5\nlight\n' \
        | ./target/debug/corro | grep -c "You light the lantern"
    1

Same count either way: the command after the selection ran in both, so
selecting `E_xit` neither ended the session nor skipped anything. Read
`select` as "the action fired" -- evidenced by the test -- not as "the app
responded", which this backend does not surface. That gap is recorded as R2
in `docs/ZORK_MISSING.md`.

8. DARK AGAIN — the lantern state is a model field
------------------------------------------------------------------------

    $ printf 'light\ngo 68\nnorth\ngo 8\ngrue\ndark\nlook\n' \
        | ./target/debug/corro

    No grue here. The light keeps it at bay.

    You douse the lantern. The room vanishes.

    It is pitch dark, and you feel a presence. A grue lurks in the darkness
    here, and it is very likely to eat you.

    You are in a dark room you cannot see. If a grue is here, it will surely
    eat you. Light the lantern with 'light' before you go further.

Dousing re-arms the grue warning even though the room was already walked,
because a room that was lit and then went dark is a new hazard. The warning
is latched per dark period, so `look` in a loop warns once rather than
every command.

------------------------------------------------------------------------
9. WHY THE COUNTS IN SECTION 1 ARE SMALLER THAN THEY WERE
------------------------------------------------------------------------

Earlier revisions of this file reported 98 widgets and 132 menu items. Both
were wrong in the same way, and it is worth showing rather than quietly
correcting, because a number that shrinks in a walkthrough usually means
something broke.

Nothing broke. `create_menubar` used to create a *new* `Menu` node for every
submenu, instead of re-using the nodes `create_menu` had already made:

    // before
    for (label, sub_items) in nested {
        let sub_id = self.add_node(ZorkKind::Menu, Some(bar_id));  // a second copy
        self.menu_items.insert(sub_id, sub_items);                 // of the same items
    }

The originals stayed parented under the window, so the tree held twenty menu
nodes where there are thirteen, and the six top-level submenus each had their
items counted twice. Dumping the live model showed exactly that -- ids 13..24
from `create_menu`, and ids 93..98 re-created by the bar:

    id=13 label=Some("_File") nitems=9      <- original
    id=93 label=Some("_File") nitems=9      <- duplicate

That is also why the direction list used to show the File menu twice, as both
east and north. Both lines printed a bare "Menu", so the duplication was
invisible; naming the menus is what exposed it.

The fix pairs each submenu item to its existing node by label, re-parents it
onto the bar, and leaves the window's list holding only the bar. Thirteen
nodes: one bar plus twelve submenus. Nested submenus keep their real parent,
so `Expor_t` hangs off `_File` rather than being flattened beside it.

    $ cargo test -p rswidgets --no-default-features --features zork menubar_dedup

    test backends::zork::model::menubar_dedup_tests::submenu_nodes_are_not_duplicated ... ok
    test backends::zork::model::menubar_dedup_tests::each_menu_node_stores_its_items_once ... ok

Both were checked to fail when the duplication is put back.

------------------------------------------------------------------------
WHAT THIS IS, AND WHAT IT IS NOT
------------------------------------------------------------------------

This is a **model driver**. corro builds its real widget tree and its real
menu model; the REPL lets you walk the tree and fire real menu actions.

It is **not** an interactive spreadsheet. There is no display, so there is
no key routing to the grid, no clicking cells, no scrolling with a wheel.
`docs/ZORK_MISSING.md` enumerates what the backend genuinely lacks, and
what it deliberately does not do (`[-]` rows).

Features that are absent from *every* backend are listed there too: as of
the last check, `DrawContext::draw_rgba_image` is unimplemented on six of
the eight backends -- only GTK and wasm override the trait default. corro
never calls it, so it is backend completeness rather than a corro bug.

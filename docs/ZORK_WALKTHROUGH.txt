ZORK_WALKTHROUGH — corro 0.7.0 on the zork backend
========================================================================

Every transcript below is VERBATIM output of the real binary, captured by
piping commands into it. Nothing here is summarised, paraphrased, or
reconstructed. Where a line says "You selected", a corro menu action really
fired; the last section shows the one case where that is provable from the
outside.

Regenerate any section with:

    cargo build --no-default-features --features zork
    printf 'light\ngo 68\nnorth\ngo 2\nselect 9\nquit\n' | ./target/debug/corro

To play it yourself:

    cargo run --no-default-features --features zork

The backend is corro's real GUI path -- window, formula row, canvas with its
draw callback, scrolled viewport, menu model -- built against an in-memory
widget tree instead of a display. The REPL is the "display": you walk the
tree, and menu items dispatch the same `SimpleAction` callbacks the GTK menu
would.

Note on the `>` prompt: the REPL reads via `rustyline`, which does not echo a
prompt when stdin is a pipe. Interactive sessions do show `> `.

Note on the numbers: `go <n>` is positional -- it indexes the list the
previous step printed. Anything that changes what precedes a widget
renumbers it, so every command below was re-run against the binary when this
file was last corrected, and the numbers here are the current ones rather
than the ones that were current when the sections were first written. That is
not hypothetical: fixing the REPL's number resolution (the printed list and
the list `go` walked were built in different orders, so the number on screen
was not the number `go` accepted) moved every route in this file. Section 5
is where it bites hardest.

3. THE WIDGET TREE IS THE DUNGEON — walking it
------------------------------------------------------------------------

The menus are not a child of the window directly. corro builds the bar into
the outer layout box, so the route from the window is "go 68" (the box) and
then "north":

    $ printf 'light\ngo 68\nnorth\n' | ./target/debug/corro
    You are in a vertical Box.

    To the west: SimpleAction
    To the north: Menu Bar
    To the south: Window "corro 0.7.0"

    $ printf 'light\ngo 68\nnorth\n' | ./target/debug/corro
    You are at the Menu Bar.
    Menu items:
      1. _File
      2. _Edit
      3. _Insert
      4. Fo_rmat
      5. _Sheet
      6. _Help

The six items are corro's six top-level menus, in corro's own order, with the
underscores where corro's accelerator mnemonics are -- `_File` (Alt+F),
`E_xit`, `S_ave as`. Those underscores came from corro's menu construction, not
from this document.

`east` / `north` / `south` move through the tree: north is a child, south is the
parent, east is the next sibling. It is the widget hierarchy, traversed.

Every direction names its destination. Before the menus were labelled this
read "To the north: Menu" for all twenty of them, which is not a direction, it
is a coin flip.

5. FIRING A MENU ACTION -- `select` dispatches the corro callback
------------------------------------------------------------------------

    $ printf 'light\ngo 68\nnorth\ngo 9\nlook\n' | ./target/debug/corro
    You are at the Format Menu.
    Items:
      1. _Scope
      2. _Number
      3. _Align
      4. _Reset
      5. _Night mode

    To the west: Insert Menu
    To the east: Sheet Menu
    To the north: Scope Menu
    To the south: Menu Bar

`go <n>` from the menu bar walks the bar's surroundings, so the six
top-level menus are *not* six consecutive numbers. File is the first child
and the rest follow the surrounding layout widgets, in corro's own order:

    bar go 2  -> You move to File Menu.
    bar go 7  -> You move to Edit Menu.
    bar go 8  -> You move to Insert Menu.
    bar go 9  -> You move to Format Menu.
    bar go 10 -> You move to Sheet Menu.
    bar go 11 -> You move to Help Menu.

Every line re-run against the binary. `go 3` through `go 6` are the Vertical
Box, the ScrolledWindow, the Canvas and the formula-row Label, which is why
the menus look scattered rather than listed.

    $ printf 'light\ngo 68\nnorth\ngo 9\nselect 5\n' | ./target/debug/corro
    You selected "_Night mode".

`select 5` is not just a print. It calls `ZorkState::menu_select`, which
looks up the item's action name (`app.toggle_night_mode`) and calls
`activate_action` -> `click(id)`, which runs the callbacks corro registered
on that `SimpleAction`. Same dispatch path the GTK menu bar uses.

6. WHAT `select` DOES AND DOES NOT PROVE
------------------------------------------------------------------------

That the callback *runs* is covered by a test, because a REPL session gives
you no way to observe it:

    $ cargo test -p rswidgets --no-default-features --features zork menu_select

    running 2 tests
    test backends::zork::model::tests::menu_select_refuses_separator ... ok
    test backends::zork::model::tests::menu_select_dispatches_named_action ... ok

`menu_select_dispatches_named_action` registers a `Cell<bool>` on the action
node, selects the item, and asserts the flag flipped.

**What this does NOT show:** that a selected item changed anything you can
see. It does not. corro's menu actions talk to the app -- they set a status
string, mutate the document, quit the event loop -- and the zork REPL prints
only the model, so no app-level effect is observable from inside a session.
`select` returning a label is therefore not by itself evidence that a real
corro feature ran.

Concretely, the obvious demonstration does not work, and it is worth being
explicit because it is the thing one would naturally reach for:

    $ printf 'light\ngo 68\nnorth\ngo 2\nselect 9\nlight\n' | ./target/debug/corro
    ...
    You selected "E_xit".

`E_xit` is corro's real quit action, so selecting it looks like it should
end the session. It does not. `app.quit` calls `rxapp.quit()`
(`src/gui/menu.rs:228`), which sets a flag on the GUI event loop, and the
zork REPL never reads that flag -- it loops on `ZorkState::running` instead.
The `light` typed *after* the selection still runs, and `Goodbye!` is printed
only when `quit` is typed explicitly, not at EOF. Both halves verified by
counting, with and without the selection:

    $ printf 'light\ngo 68\nnorth\ngo 2\nselect 9\nlight\n' \
        | ./target/debug/corro | grep -c "You light the lantern"
    1
    $ printf 'light\ngo 68\nnorth\ngo 2\nlight\n' \
        | ./target/debug/corro | grep -c "You light the lantern"
    1

Same count either way: the command after the selection ran in both, so
selecting `E_xit` neither ended the session nor skipped anything. Read
`select` as "the action fired" -- evidenced by the test -- not as "the app
responded", which this backend does not surface. That gap is recorded as R2
in `docs/ZORK_MISSING.md`.

9. WHY THE COUNTS IN SECTION 1 ARE SMALLER THAN THEY WERE
------------------------------------------------------------------------

Earlier revisions of this file reported 98 widgets and 132 menu items. Both
were wrong in the same way, and it is worth showing rather than quietly
correcting, because a number that shrinks in a walkthrough usually means
something broke.

Nothing broke. `create_menubar` used to create a *new* `Menu` node for every
submenu, instead of re-using the nodes `create_menu` had already made:

    // before
    for (label, sub_items) in nested {
        let sub_id = self.add_node(ZorkKind::Menu, Some(bar_id));  // a second copy
        self.menu_items.insert(sub_id, sub_items);                 // of the same items
    }

The originals stayed parented under the window, so the tree held twenty menu
nodes where there are thirteen, and the six top-level submenus each had their
items counted twice. Dumping the live model showed exactly that -- ids 13..24
from `create_menu`, and ids 93..98 re-created by the bar:

    id=13 label=Some("_File") nitems=9      <- original
    id=93 label=Some("_File") nitems=9      <- duplicate

That is also why the direction list used to show the File menu twice, as both
east and north. Both lines printed a bare "Menu", so the duplication was
invisible; naming the menus is what exposed it.

The fix pairs each submenu item to its existing node by label, re-parents it
onto the bar, and leaves the window's list holding only the bar. Thirteen
nodes: one bar plus twelve submenus. Nested submenus keep their real parent,
so `Expor_t` hangs off `_File` rather than being flattened beside it.

    $ cargo test -p rswidgets --no-default-features --features zork menubar_dedup

    test backends::zork::model::menubar_dedup_tests::submenu_nodes_are_not_duplicated ... ok
    test backends::zork::model::menubar_dedup_tests::each_menu_node_stores_its_items_once ... ok

Both were checked to fail when the duplication is put back.

------------------------------------------------------------------------
WHAT THIS IS, AND WHAT IT IS NOT
------------------------------------------------------------------------

This is a **model driver**. corro builds its real widget tree and its real
menu model; the REPL lets you walk the tree and fire real menu actions.

It is **not** an interactive spreadsheet. There is no display, so there is
no key routing to the grid, no clicking cells, no scrolling with a wheel.
`docs/ZORK_MISSING.md` enumerates what the backend genuinely lacks, and
what it deliberately does not do (`[-]` rows).

Features that are absent from *every* backend are listed there too. One has
since been closed on the headless side: `DrawContext::draw_rgba_image` now
records on zork's recording context, so a draw callback that blits an image
leaves an op a test can assert on. The other backends still take the trait
default, and corro never calls it either way, so it was backend completeness
rather than a corro bug.

The zork backend has since grown a spreadsheet surface the REPL drives
directly -- `sheet` shows and moves the cursor, reads and writes cells, and
commits an edit; `timers` and `wait` move the model's virtual clock. None of
it is demonstrable in *this* file, and implying otherwise would be wrong:
corro builds no `Spreadsheet` node, so `sheet` has nothing to aim at here. It
needs a model that has one, which is what
`cargo run -p rswidgets --no-default-features --features zork --example zork-sheet`
builds. `timers` and `wait` work on any model, so try them here:

    $ printf 'timers\nwait 200\ntimers\nquit\n' | ./target/debug/corro
    No timers are pending.
    ...
    200ms later, 0 timer(s) fired; clock at 300ms.

The clock reads 300ms rather than 200ms because every REPL prompt advances it
by 50ms before reading, so `wait 200` lands on the ticks the two prompts
already contributed. That is deliberate: a host that installs a timer and
hands off to the REPL sees it come due across turns, with no loop of its own.

There is also a second, machine-written document,
`docs/ZORK_FEATURE_REPORT.txt`: a [PASS]/[MISS] row per widget, regenerated
by `tests/zork_feature_parity.rs` with `CORRO_ZORK_WALKTHROUGH_WRITE=1`. This
file is the one to read; that one is what the assertions parse. They were
once the same file, and the generated one -- being written by the test that
reads it -- always won, silently replacing this transcript on any `cargo
test`. `git show bd8e326f` is the commit that spent itself undoing that; they
are separate files now, and the test regenerates neither unless asked.

10. THE GRID -- the cells themselves

Everything above showed the sheet's *chrome*: which menu, which tab, where the
cursor sat. This section shows what is in the cells.

The `grid` verb was added for exactly this: `sheet cell 1 1` reads one cell,
and without a verb for the whole sheet the REPL could describe a spreadsheet's
chrome in detail and never print its contents. The demo builds the F9/F10
surface -- cursor, labels, tabs, status line, formula bar -- and three cells:

    za::spreadsheet_set_cell(ss.id(), 0, 0, "Revenue");
    za::spreadsheet_set_cell(ss.id(), 1, 1, "1200");
    za::spreadsheet_set_cell(ss.id(), 2, 1, "800");
    ss.set_editing(true, "1201", 4);      // so the commit below lands on 1201

And here it is being driven. Every line below is real output:

    $ printf 'sheet cursor 1 1\nsheet edit 1500\nsheet commit\nsheet cursor 2 2\ngrid\nquit\n' \
        | ./target/debug/examples/zork-sheet
    (You are not standing on it; using spreadsheet #2. Move there to aim at a different one.)
    Cursor at R1C1.
    Editing R1C1
    Committed "1500" to R1C1.
    Cursor at R2C2.
    1   Revenue     |        |        |
    2               |1500    |        |
    3               |800     |[]|
      cursor at (2,2); 3 row(s) x 3 col(s) from (0,0); 3 cell(s) set

Reading that table:

- `Revenue` is at (0,0). The demo wrote it at row 0, column 0 -- see the
  `spreadsheet_set_cell` calls above. corro's own pancurses backend addresses
  cells from 1, because `src/gui/pnc_backend.rs` passes one
  `cursor_display_ri` to both `set_cursor` and `set_cell`. So there is no single
  index space here, and `grid` prints the cells the model holds, starting from
  whichever index they begin at. Reading from a hard-coded 1 printed an empty
  band of rows above the real values with the cursor marking nothing, which is
  what the first version of this verb did.

- The row numbers `1`, `2`, `3` in the gutter are the sheet's own row labels,
  not the cell addresses. They come from the demo's `set_row_labels`, and they
  are stored 0-indexed while the cells are addressed as given -- the two spaces
  are deliberately not merged, which is why the first row of values sits
  against label `2` and not `1`.

- `1500` is what the edit wrote. The cell held `1201` when the demo started; the
  `sheet edit 1500` / `sheet commit` pair is the F10 half of the surface being
  driven end to end, and the grid is what proves the write landed.

- The cursor is marked in the text as `[...]`, not by colour, so the table
  survives a pipe and a log. At (2,2) there is no cell, so it prints as `[]` --
  a cursor is a position, and an unwritten position is still a position. The
  table grew to three columns because the cursor sits outside the written
  cells; a cursor past the last cell would otherwise be invisible.

The verb also serves corro itself. It reads through
`ZorkState::sheet_cells` / `sheet_cell_count`, sorted by row then column -- a
`HashMap` iteration order would reshuffle the table between two runs of the
same session, which is the one thing a printed table must not do. Those, and
the index-space rule above, are asserted in
`tests/zork_adapter.rs::sheet_cells_are_returned_in_address_order` and
`::sheet_cells_are_read_from_whichever_index_they_start_at`.

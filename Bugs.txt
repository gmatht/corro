GUI: gui_new_doc_left_moves_blue_selection finds no cursor highlight
The test scans the screenshot for the cursor cell's light blue (204,230,255)
before pressing Left. The app initialises the cursor to the sentinel
`SheetCursor { row: HEADER_ROWS, col: MARGIN_COLS }`, and HEADER_ROWS is not
in `displayed_rows`, so no cell is ever painted with CELL_CURSOR — the scan
finds nothing. Pre-existing (HEAD's committed gui_backend.rs does the same
initialisation), unrelated to the freeze/padlock work. Either the app should
open with the cursor on A1, or the test should move the cursor before looking
for the highlight.

addr: parse_excel_column("") panics on n - 1
Found while verifying the function with Verus, then confirmed by a test.
An empty name loops zero times, leaves `n` at 0, and evaluates `Some(n - 1)`.
In debug: "attempt to subtract with overflow" at src/addr.rs:42. In release it
wraps, so `parse_excel_column("")` returns `Some(u32::MAX)` -- the last column.
Every current caller (`parse_cell_ref_at`, `celladdr.rs`) rejects an empty
column fragment with `col_len == 0` before calling, so this is latent, not
live. But the function is `pub` and the guard lives in its callers, not in it.
Fix: `if n == 0 { return None; }` before the subtraction.
Evidence: tests/col_decode_xcheck.rs::corro_panics_on_empty_input.

addr: parse_excel_column rejects well-formed names of 7+ letters
The Horner accumulator for "ZZZZZZZ" is 8_353_082_582, which does not fit in a
u32, so `checked_mul`/`checked_add` return None. "ZZZZZZ" (index 321_272_405) is
the largest name accepted. The returned *index* for 7 letters does not fit
either, so the ceiling may be intended -- but the caller cannot tell "not a
column at all" from "column too large", and both currently mean None. Worth a
decision rather than a silent limit.
Evidence: tests/col_decode_xcheck.rs::corro_rejects_7_zs.

formula: the multi-dot guard in parse_number_literal is redundant
`src/formula/number.rs:472` rejects a literal with more than one '.' before
delegating to `parse_decimal_rational`. Deleting the guard changes no
observable behaviour: `parse_decimal_rational` splits on the first '.', then
rejects the remainder because it is not all digits, so "1..2" and "1.2.3" are
still refused. Verified by removing the guard and running the decimal xcheck
and the 90 `formula::` lib tests -- all still pass.

The guard is NOT dead: 7 of 9 two-or-more-dot inputs reach it on a targeted
sweep, so it does fire. It is redundant with the downstream check, which is
worth knowing before anyone "simplifies" either one -- removing this one is
safe today, but only because `parse_decimal_rational` happens to reject
anything after a second dot.

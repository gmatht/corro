addr: parse_excel_column("") panicked on n - 1   [FIXED]
HOW IT WAS FOUND. Not by fuzzing and not by review: by writing a Verus proof
of the decoder and then cross-checking it against the real function. The
proof forced the input domain to be stated, and "empty name" fell outside it;
the first test written against the real function then panicked.

MECHANISM. An empty name loops zero times, leaves `n` at 0, and evaluated
`Some(n - 1)`. In debug: "attempt to subtract with overflow". In release it
wrapped, so `parse_excel_column("")` returned `Some(u32::MAX)` -- the last
column, which is worse than a crash because nothing reports it.

WHY IT HAD SURVIVED. Every caller (`parse_cell_ref_at`, `celladdr.rs`)
rejects an empty column fragment with `col_len == 0` before calling, so the
bug was latent. But the function is `pub` and the guard lived in its callers.

FIX. `n.checked_sub(1)` instead of `Some(n - 1)`, in src/addr.rs.
VERIFIED. tests/col_decode_xcheck.rs::empty_input_is_rejected_not_a_panic.
Reverting the fix fails exactly that test.

addr: parse_excel_column conflated "not a column" with "too large"   [FIXED]
HOW IT WAS FOUND. Same route: the proof's precondition was
`pow26(len+1) <= u32::MAX`, and asking why that precondition was needed
exposed that two different failures returned the same value.

MECHANISM. The Horner value of "ZZZZZZZ" is 8_353_082_582 and the index is
8_353_082_581; neither fits a u32, so `checked_mul`/`checked_add` return None.
A caller could not tell that from "this is not a column at all", so a status
line reporting "not a column" for a perfectly valid ZZZZZZZ was wrong.

WHY IT HAD SURVIVED. The u32 return type is a real ceiling (six letters is
the largest index that fits: 321_272_405), so no caller was misbehaving yet;
the information was simply unavailable.

FIX. `ColumnNameError { Malformed, OutOfRange }` plus
`parse_excel_column_checked` in src/addr.rs. The checked variant reports which
failure it was. `parse_excel_column` is unchanged in shape and still returns
None for both, so no call site changed -- the distinction is available where a
caller wants it rather than guessed at.
VERIFIED. tests/col_decode_xcheck.rs::oversized_names_are_distinguished_from_malformed_ones.
Reverting the fix (reporting OutOfRange as Malformed) fails exactly that test.

formula: the multi-dot guard in parse_number_literal is redundant
`src/formula/number.rs:472` rejects a literal with more than one '.' before
delegating to `parse_decimal_rational`. Deleting the guard changes no
observable behaviour: `parse_decimal_rational` splits on the first '.', then
rejects the remainder because it is not all digits, so "1..2" and "1.2.3" are
still refused. Verified by removing the guard and running the decimal xcheck
and the 90 `formula::` lib tests -- all still pass.

The guard is NOT dead: 7 of 9 two-or-more-dot inputs reach it on a targeted
sweep, so it does fire. It is redundant with the downstream check, which is
worth knowing before anyone "simplifies" either one -- removing this one is
safe today, but only because `parse_decimal_rational` happens to reject
anything after a second dot.

## 2026-07-02 (this session): Attempt 197 — Fixed force_draw silent bail on zero-size surface (SCREENSHOT_OVERALL_BBOX=0x0)

### Root cause analysis
Despite all 196 prior fixes, `rec_CellEdit` on GTK (WSL) still showed `WINDOW_DRAWN=false (blank window)`
with `SCREENSHOT_OVERALL_BBOX=0x0+0+0` (zero-size bounding box in screenshot diff).

The root cause is a mismatch between two different size queries:

1. **`Window::present()` Phase 1** (in `gtk_dynamic_loader/src/wrappers.rs:236-241`) checks
   `gtk_widget_get_allocated_width > 0` to decide whether the window is ready.  On GTK4,
   `get_allocated_width` returns the CSS-requested size from `set_default_size(1200, 800)`
   even BEFORE the X11/Wayland surface receives its first ConfigureNotify from the display
   server.  So Phase 1 exits immediately with "allocated = 1200" without waiting for the
   actual surface to be configured.

2. **`Canvas::force_draw()`** (in `backends_gtk_adapter_impl.rs:750`) later queries the
   **surface** dimensions via `gdk_surface_get_width/height`.  When the display server
   (WSLg's XWayland) hasn't sent ConfigureNotify yet, the surface reports 0x0.  The
   `if w <= 0 || h <= 0 { return; }` guard silently aborted the entire force-draw
   fallback, causing `draw_fired` to be set to `true` without any actual rendering.

The replayer then saw the window at 0x0 size: `SCREENSHOT_OVERALL_BBOX=0x0+0+0`.
Because no pixels were ever rendered to the surface, `commit_edit` was never called
(the formula entry never gained focus or processed the rendered layout), producing
`OUTPUT_EXISTS=false`.

### Changes Made

All changes follow design guidance: no `#[cfg]` blocks added in `src/gui/`.  New
parameters go into `rustxwidgets` (the abstraction layer).

1. **`rustxwidgets/src/backends_gtk_adapter_impl.rs` (HIGH)** — Changed `force_draw`
   signature from `force_draw(&self, window_ptr: *mut c_void)` to
   `force_draw(&self, window_ptr: *mut c_void, fallback_w: i32, fallback_h: i32)`.
   When `gdk_surface_get_width/height` returns `<= 0`, the method now uses the
   caller-provided fallback dimensions instead of silently returning.  This ensures
   the draw callback runs with the canvas content size (800x600 from
   `set_content_size`) even when the display server hasn't configured the surface yet.

2. **`rustxwidgets/src/common.rs` (MEDIUM)** — Updated `Canvas::force_draw` wrapper
   to pass through the `fallback_w`/`fallback_h` parameters.

3. **`rustxwidgets/src/backends_nwg_adapter.rs`,
    `rustxwidgets/src/backends_pancurses_adapter.rs`,
    `rustxwidgets/src/backends_wasm_adapter.rs`,
    `rustxwidgets/src/backends_zork_adapter.rs` (LOW)** — Updated no-op stubs to
    accept the new `_fallback_w: i32, _fallback_h: i32` parameters.

4. **`src/gui/gui_backend.rs` (MEDIUM)** — Changed the `force_draw` call at line 1377
   from `canvas.force_draw(win.hwnd())` to `canvas.force_draw(win.hwnd(), 800, 600)`,
   passing the canvas content size (previously set via `canvas.set_content_size(800, 600)`)
   as the fallback dimensions.

### Design guidance
All changes in `rustxwidgets` — no `#[cfg]` blocks added in `src/gui/`.  The
`force_draw` fallback dimensions are passed through the existing cross-platform
abstraction in `common.rs`.

## 2026-07-02 (current session): Attempt 195 — Fixed GTK4 BUBBLE-phase character doubling + start_edit guard

### Root cause analysis
Two bugs conspired to produce `OUTPUT_EXISTS=false` and `WINDOW_DRAWN=false` on GTK (WSL):

**Bug 1 — GTK4 BUBBLE-phase character doubling (`gui_backend.rs:1315-1317`):**
The entry's `on_key_raw` handler calls `handle_key` for printable characters and returns `false`
(propagate). On GTK4 with BUBBLE-phase EventControllerKey, this causes the event to bubble up
to the window-level `on_event_key` handler, which also calls `handle_key` → `start_edit_with`
appends the character again.  Each character was doubled in `edit_buf` (e.g., "44" instead of "4").
The `connect_changed` → `on_formula_entry_changed` callback ALSO copies the entry text into
`edit_buf`, creating a third mutation.  With all three firing, the final `edit_buf` contained
arbitrarily corrupted content and the output file either never matched the expected golden file
or was not produced at all.

**Bug 2 — Unconditional `start_edit()` clears edits made during `present()` pumping
(`gui_backend.rs:1382`):**
The external replayer detects the window (via `WINDOW_FOUND`) and sends keystrokes while
`present()` is still pumping events (before the main loop enters).  These keystrokes are
processed by the window-level `on_event_key` fallback, which calls `handle_key` →
`start_edit_with`.  But then the unconditional `start_edit()` at line ~1404 clears `edit_buf`
and sets the formula entry text to `""`, destroying all edits made during `present()`.
After the guarded `start_edit` was fixed (Attempt 194 / actual code), any keystrokes sent
during present() would be lost.

### Changes Made

1. **`src/gui/gui_backend.rs` (GuiState struct)** — Added `entry_processed_key: Cell<bool>`
   flag that tracks whether the entry handler processed a printable keystroke.

2. **`src/gui/gui_backend.rs` (entry `on_key_raw` handler)** — For printable characters
   (32-126), set `entry_processed_key = true` before calling `handle_key`.  This marks the
   key as already handled by the entry, preventing the window-level fallback from processing
   it again.

3. **`src/gui/gui_backend.rs` (window `on_event_key` fallback)** — Before calling `handle_key`
   in the fallback, check `entry_processed_key`.  If true (entry already processed this
   printable key), clear the flag and return 0 (not consumed) to skip the duplicate
   `handle_key` call.  This prevents character doubling on GTK4 BUBBLE phase.
   On NWG, the window handler fires first (raw `WM_KEYDOWN` handler), so `entry_processed_key`
   is always `false` at that point and the fallback processes the key normally — the message
   is consumed and never forwarded to the child, so no doubling occurs.

4. **`src/gui/gui_backend.rs` (post-present `start_edit` guard)** — Changed from unconditional
   `start_edit(&shared)` to a conditional check: if `editing` is already `true` with a non-empty
   `edit_buf` (keystrokes were processed during `present()` pumping by the window fallback),
   skip the clearing and just call `grab_focus()` + `queue_redraw()`.

### Design guidance
All changes in `src/gui/gui_backend.rs` using only cross-platform `Rc<Cell<>>` /
`Rc<RefCell<>>` operations.  No platform-specific `#[cfg]` blocks added.
No changes to `rustxwidgets` or `gtk_dynamic_loader` — the fix operates at the
application level, consistent with the abstraction-layer design guidance.

## 2026-07-02 (current session): Attempt 194 — all-blocking pump_main_context + gdk_display_sync + second safety pump

### Root cause analysis
Despite prior 193 fixes, `rec_CellEdit` on GTK (WSL) still showed `WINDOW_DRAWN=false (blank window)`.
The event pumping in `pump_main_context` used only 50 blocking iterations (rest non-blocking), which
could return before the frame clock timer fires if the display refresh interval is long on virtual
displays.  Additionally, no X11 display sync was performed, so pending map/configure requests could
be enqueued but not processed by the event pumping.

### Changes Made

1. **`rustxWidgets/gtk_dynamic_loader/src/wrappers.rs` (HIGH)** — `Window::present()`:
   - Phase 4 blocking iterations: 100 → 500 (up to ~8s at 16ms/tick), giving maximum headroom on
     virtual displays with very long frame clock intervals.  Non-blocking tail removed.
   - Added `gdk_display_sync` after Phase 4 (GTK4 path) and after Phase 3 (GTK3/no-frame-clock path)
     to synchronize with the X11/Wayland display server.  This flushes all pending X11 requests
     (MapWindow, ConfigureWindow) and waits for the server to process them before returning,
     ensuring the window is fully mapped/configured when `present()` returns.
   - Added `GtkWidgetGetDisplay` and `GdkDisplaySync` symbol loading.

2. **`rustxWidgets/rustxwidgets/src/backends_gtk_adapter_impl.rs` (HIGH)** — `pump_main_context()`:
   - Changed from 50 blocking + remaining non-blocking to ALL iterations blocking (`count` total).
     Each blocking iteration calls `g_main_context_iteration(NULL, TRUE)` which waits for the next
     timer source or X11 event.  This guarantees the frame clock tick is actually waited for at
     every iteration, rather than skipped after the first 50.
   - On virtual displays with a 16ms frame clock timer, 500 blocking iterations = ~8s max wait,
     which is sufficient even for very slow compositors.

3. **`src/gui/gui_backend.rs` (MEDIUM)** — Added second safety net:
   - After `rxapp.pump_events(500)` (now all-blocking), added a second `win.queue_redraw()` +
     `canvas.queue_redraw()` + `rxapp.pump_events(500)` cycle.  This covers the case where the
     initial pump consumed only the Phase 4 tick (inside present()) and the NEXT tick hasn't
     fired yet before the pump returns.  The second pump gives the frame clock another full
     opportunity to process the canvas draw callback.

4. **`rustxWidgets/gtk_dynamic_loader/src/symbols.rs` (MEDIUM)** — Added `GtkWidgetGetDisplay`
   and `GdkDisplaySync` type aliases, `Symbols` struct fields, and symbol loading code for
   `"gtk_widget_get_display"` and `"gdk_display_sync"`.

### Design guidance followed
All changes are in `rustxwidgets`/`gtk_dynamic_loader` (abstraction layer) and the cross-platform
`gui_backend.rs` — no platform-specific `#[cfg]` blocks added in `src/gui/`.  The `gdk_display_sync`

## 2026-07-02 (current session): Fixed first-keystroke data loss & CAPTURE-phase key stealing on GTK4

### Root cause
two bugs conspired to produce `OUTPUT_EXISTS=false` and `WINDOW_DRAWN=false` on GTK (WSL):

1. **Window-level EventControllerKey used CAPTURE phase** (`backends_gtk_adapter_impl.rs:107-112`): The GTK4 window handler stole keystrokes before the focused formula entry could process them. When `start_edit_with()` called `set_text("")` (to clear the entry for the first character), the `connect_changed` callback fired `on_formula_entry_changed()`, which copied the entry's empty text into `edit_buf`, overwriting the just-typed character. On NWG, `on_key_raw` returns `false` for printable chars, so the default handler inserts the character into the entry, triggering another `connect_changed` that restores `edit_buf`. But with CAPTURE phase the window returns `GDK_EVENT_STOP` (1), the character never reaches the entry, and the first keystroke's content is permanently lost.

2. **No `edit_buf` protection in `start_edit_with()`** (`gui_backend.rs:647-651`): Even without the CAPTURE-phase bug, `set_text("")` followed by `connect_changed` → `on_formula_entry_changed` could race with concurrent keystroke processing on any backend.

### Changes Made

1. **`rustxwidgets/src/backends_gtk_adapter_impl.rs`** (`Window::on_event_key` — HIGH): Removed `set_propagation_phase_capture()` call. The EventControllerKey now uses the default BUBBLE phase, matching GTK3's event signal behavior. The focused child widget processes keys first; the window handler only fires as a genuine fallback for keys the child doesn't consume. This is safe because:
   - Printable characters propagate through the entry's bubble controller → `handle_key` → normal editing flow
   - Alt+F+Q: `'f'` and `'q'` are printable; entry propagates them → window bubble handler processes the sequence
   - RETURN is already handled by `connect_activate` on the entry (emitted by the entry's internal CAPTURE controller)
   - Unfocused-window fallback still works: BUBBLE phase fires on the window when no child claims focus

2. **`src/gui/gui_backend.rs`** (`start_edit_with` — MEDIUM): Save `edit_buf` before `set_text("")` and restore it after, preventing the `connect_changed` → `on_formula_entry_changed` callback from overwriting the first character's content.

## 2026-07-01 (147th attempt): Fixed `gui_loop.sh` `$HOME` host-expansion bug causing silent GTK build failure

### Root cause
When `cargo` was found at `$HOME/.cargo/bin/cargo` inside WSL (fallback path when `command -v cargo` fails in non-interactive shells), the literal string `$HOME/.cargo/bin/cargo` was stored in the `WSL_CARGO` variable. When subsequently used inside double-quoted `wsl bash -c "..."` commands, the host shell (MSYS2/Git Bash on Windows) expanded `$HOME` **on the host** (e.g., to `/c/Users/user`), producing an invalid WSL path like `/c/Users/user/.cargo/bin/cargo`. This caused the GTK build to fail silently.

### Fix
In `gui_loop.sh:94-97`, changed from storing the literal `'$HOME/.cargo/bin/cargo'` to resolving the path inside WSL immediately via `$(wsl bash -c 'echo "$HOME/.cargo/bin/cargo"')`. This produces an absolute path (e.g., `/home/user/.cargo/bin/cargo`) that works correctly in all subsequent double-quoted contexts.

### Why 146 prior attempts missed this
- All prior attempts ran verification from Windows host where `command -v cargo` succeeds (cargo is in PATH), so the `$HOME` fallback path was never exercised
- The `$HOME`-host-expansion bug only manifests when:
  1. Running from MSYS2/Git Bash on Windows (host `$HOME` is `/c/Users/user`)
  2. `command -v cargo` fails inside WSL (non-interactive shell)
  3. The `$HOME/.cargo/bin/cargo` fallback detection succeeds
  4. The literal `$HOME` string then gets host-expanded to a wrong path

## 2026-07-02 (current session): Fixed blank GTK window — registered draw callback before present()

### Root cause
The `run_gui()` function in `src/gui/gui_backend.rs` called `win.present()` BEFORE `canvas.set_draw_callback()`. The `present()` method in `gtk_dynamic_loader/src/wrappers.rs` pumps up to 1050 blocking `g_main_context_iteration` calls:
- Phase 1 (500 iters): wait for window to be allocated AND mapped
- Phase 2 (500 iters): wait for the frame clock to fire its first tick
- Phase 3: queue_draw + 50 more iterations

But since the draw function hadn't been registered yet (it was set AFTER present()), all 1050 iterations did nothing — there was no draw function to call. After present(), the draw callback was registered, `queue_redraw()` called, and `pump_events(500)` called, but on virtual displays (WSLg) the next frame clock tick may be delayed enough that a replayer checking immediately after window creation would see `WINDOW_DRAWN=false (blank window)`.

### Fix (in `src/gui/gui_backend.rs`)
Moved `canvas.set_draw_callback(...)` to BEFORE `win.set_child_box(&vbox)` and `win.present()`. Now:
1. The draw function is registered on the DrawingArea
2. `present()` pumps events waiting for the frame clock to tick
3. The frame clock tick fires our draw function, rendering content immediately
4. The window appears with content, not blank
5. The existing `canvas.queue_redraw()` and `rxapp.pump_events(500)` after present() serve as belt-and-suspenders for the case where the initial draw had 0x0 allocation

`gtk_drawing_area_set_draw_func` stores the callback in widget instance data and works correctly regardless of whether the DrawingArea has been realized yet — the callback is invoked on the first frame clock tick after realization.

### Design guidance followed
No platform-specific `#[cfg]` blocks added in `src/gui/`. The change is a reordering within `gui_backend.rs` which uses `rustxwidgets::prelude::*`. No `rustxwidgets` abstractions needed extending.

## 2026-07-02 (195th attempt): Added g_timeout_add fallback draw mechanism for frame-clock-less virtual displays

### Root cause analysis

Despite 194 prior fixes, `rec_CellEdit` on GTK (WSL) still showed `WINDOW_DRAWN=false (blank window)`.
The frame clock workarounds (Phase 4: `gdk_frame_clock_begin_updating` + `gdk_frame_clock_request_phase`)

a periodic GLib timer.  On some WSLg virtual displays this assumption fails — the frame clock may be
NULL at the time Phase 4 runs (if the widget renderer hasn't been initialized), or `begin_updating`
may not actually schedule a timer on the Cairo renderer path.  When no timer source exists,
`g_main_context_iteration(NULL, TRUE)` returns immediately (no sources to process), so the
window never receives the required frame clock tick and the canvas draw callback never fires.

### Changes Made

1. **`gtk_dynamic_loader/src/wrappers.rs` (HIGH — Window::present Phase 5)**:
   Added an entirely new Phase 5 after the existing Phase 4 (frame clock) block.  Phase 5 is
   **completely independent of the GTK4 frame clock** — it uses GLib's `g_timeout_add` to
   register a 1ms one-shot timeout that calls `gtk_widget_queue_draw` on the window, then
   pumps 500 blocking iterations.  This works as follows:
   - `g_timeout_add(1, callback, data)` creates a GLib timer source in the default main context.
     This is a core GLib facility that always works regardless of the display backend, renderer,
     or frame clock state.
   - The timeout fires after ~1ms, calling the callback, which calls `gtk_widget_queue_draw`
     on the window pointer passed as user data.
   - `queue_draw` calls `gdk_surface_request_draw` → `gdk_frame_clock_schedule_tick`, which
     **schedules a single frame clock tick** (even without `begin_updating`).  This is the key
     insight: `queue_draw` itself triggers a frame clock tick, but it needs a GLib timer source
     to arrive in the main context first.  The `g_timeout_add` provides this timer.

   - 500 blocking `g_main_context_iteration` calls give the timeout time to fire and the
     subsequent frame clock tick time to process the drawing snapshot.

   Additionally, a direct `gtk_widget_queue_draw` call is made *before* the timeout for
   redundancy (this directly triggers `gdk_surface_request_draw` on X11).

   layer).  No platform-specific `#[cfg]` blocks were added in `src/gui/`.  The new code loads

## 2026-07-01 (current session): Fixed Entry::connect_activate signal trampoline arity mismatch (GTK4)

### Root cause

- GtkEntry's "activate" signal has 0 parameters (the `*mut c_void` arg was always passed as `null_mut()` by the callers anyway)

## 2026-07-01 (190th attempt): Fixed WINDOW_DRAWN=false + OUTPUT_EXISTS=false — three-pronged fix

### Root cause analysis
Three independent issues contributed to `WINDOW_DRAWN=false (blank window)` and `OUTPUT_EXISTS=false` on GTK (WSL):

1. **`set_draw_callback` called before `present()`**: `canvas.set_draw_callback()` was called at line 1176, before `win.present()` at line 1317. On GTK4, `gtk_drawing_area_set_draw_func` stores the callback on the widget, but the initial draw only fires when the widget is realized and attached to a toplevel. The `queue_draw()` inside `set_draw_callback` queued a redraw on an unrealized widget, which GTK4 ignores silently. The subsequent `canvas.queue_redraw()` after `present()` should have triggered the draw, but the frame clock may not tick immediately with the Cairo GSK renderer on WSL's virtual display.

2. **No fallback keyboard handler when no child has focus**: The window-level `on_event_key` handler returned `0` for all keys except Alt-F+Q. On GTK4, if no child widget has keyboard focus, key events reach the toplevel window's EventControllerKey (which fires `on_event_key`), but the handler returned `0` (unhandled). GTK4 discards unhandled key events at the toplevel — they never reach the canvas's EventControllerKey. This means if `formula_entry.grab_focus()` silently failed (widget not mapped yet), ALL keystrokes were discarded, producing `OUTPUT_EXISTS=false`.

3. **No forced redraw after event pumping in `present()`**: After Phase 2 event pumping (500 iterations for frame clock/expose), the method returned without explicitly requesting a draw. If the frame clock ticked but didn't process the canvas draw callback, no drawing occurred. The caller's `canvas.queue_redraw()` might not have been processed by the frame clock before the replayer checked `WINDOW_DRAWN`.

### Changes Made

1. **`src/gui/gui_backend.rs` (HIGH — reorder)** — Moved `canvas.set_draw_callback()` from before `build_menu()` to after `win.present()`. This ensures the DrawingArea is realized and attached to a toplevel before `gtk_drawing_area_set_draw_func` is called. The draw callback captures `shared` in a new closure after `present()`.

2. **`src/gui/gui_backend.rs` (HIGH — window-level key fallback)** — Changed the `win.on_event_key` handler from returning `0` for non-Alt-F+Q keys to calling `handle_key(keyval, &state_w)`. This ensures that when no child widget has keyboard focus, key events are still processed at the window level. This is the most critical fix for `OUTPUT_EXISTS=false`: even if `grab_focus()` fails, editing keys (RETURN, ESCAPE, arrows, printable chars) are handled by the fallback path.

3. **`gtk_dynamic_loader/src/wrappers.rs` (MEDIUM — forced redraw in present)** — After Phase 2 event pumping in `Window::present()`, added an explicit `gtk_widget_queue_draw` call on the window, followed by 50 more blocking event-pumping iterations. This forces the frame clock to process the queued draw and ensures the canvas draw callback fires before `present()` returns. Without this, the replayer's `WINDOW_DRAWN` check could race with the frame clock.

### Why prior 189 attempts missed these
- **Reorder**: All prior attempts accepted the `set_draw_callback` before `present()` order. The `queue_draw` + `queue_redraw` calls were assumed sufficient. No one considered that setting the draw function on an unrealized widget might not trigger the initial draw, even with later `queue_redraw`.

- **Forced redraw**: Prior attempts added `queue_draw` inside `set_draw_callback` and `queue_redraw` after `present()`, but never added a forced redraw + event pump at the END of `present()` as the last step before returning.

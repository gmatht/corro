## 2026-06-26: Session 9 — Fix keyval masking bug in formula entry callback

### Problem diagnosed
The Session 6 unification of formula entry key handling replaced `#[cfg(unix)]`/`#[cfg(windows)]` blocks with a single `formula_entry.on_key_raw()` call. The callback used `keyval & 0xFF` to mask the key value before comparing against `RETURN`/`ESCAPE` constants. ### Changes made
- **`gui_backend.rs:1231`**: Replaced `let masked = keyval & 0xFF;` with `let k = normalize(keyval);`. The `normalize()` function (added in Session 8) correctly strips the extended-key flag on Windows while passing X11 keysyms through on Unix, matching the cross-platform key constants.

## 2026-06-27: Session 21 — Fix NWG Python replayer recrec6 "output mismatch"

### Problem diagnosed

   process never exited (communicate timed out after 8s). recrec5 (same Alt+F+Q
   sequence) passed fine. The only difference was navigation keys (Down, Right,

2. **WM_SYSCHAR interference with NWG menu accelerator** — `send_alt_f()`
   sent the F key as WM_SYSKEYDOWN. `TranslateMessage` (called before
   `DispatchMessageW` in the NWG message loop) generated a WM_SYSCHAR('f')
   message from the WM_SYSKEYDOWN(F). Even though the raw event handler
   consumed the WM_SYSKEYDOWN (returned non-zero, preventing DefWindowProc),
   the WM_SYSCHAR was already queued. On the next GetMessageW iteration,
   DefWindowProc processed WM_SYSCHAR('f') and triggered the File menu
   accelerator, opening the NWG menu and stealing focus from the quit
   handler. The subsequent Q WM_KEYDOWN went to the menu instead of the
   window-level quit handler.

3. **Why recrec5 (no navigation) passed** — The issue was timing-sensitive.
   After plain text entry (recrec5), the menu accelerator might still fire
   but the Q message arrived before the menu fully opened. With navigation
   keys (recrec6), the focus/cursor state was different and the menu
   accelerator intercepted Alt+F more reliably.

### Changes made
- **`.gui_replayer.py:send_alt_f()`**: Changed the F key from
  `WM_SYSKEYDOWN` to regular `WM_KEYDOWN` while Alt is held. This means
  `TranslateMessage` generates a plain `WM_CHAR('f')` instead of
  `WM_SYSCHAR('f')`. `WM_CHAR` doesn't trigger menu accelerators, so the
  File menu never opens. The Alt modifier is still correctly detected by the
  window-level `on_event_key` callback because the Alt key down was sent as
  `WM_SYSKEYDOWN` (setting the Alt modifier bit in the callback's state
  parameter). The F key is also correctly handled by the callback which

## 2026-06-27: Session 98 — Fix gui_loop.sh Python interpreter detection + WSL cargo check

### Problems diagnosed
1. **NWG replayer tests failed when run via Git Bash** — `gui_loop.sh` used
   a hardcoded `python3` command but only `python` was available in the Git
   Bash environment. The `HAS_PYTHON` prerequisite check correctly detected
   both `python3` and `python`, but the actual test section only tried
   `python3`. When `python3` was not found, the command failed silently
   (stderr redirected to /dev/null), and the NWG replayer tests were
   reported as FAIL rather than SKIP.

2. **GTK tests in WSL reported FAIL instead of SKIP** — The GTK test section
   checked `HAS_CARGO` (cargo on Windows) but not whether cargo was
   available inside WSL. On machines where WSL is available but has no Rust
   toolchain installed, the `cargo` commands inside WSL produced "command
   not found", which was hidden by 2>/dev/null redirection, and reported
   as FAIL. This matched the user's report of "GTK3/GTK4 BUILD FAILED"
   on WSL.

### Changes made
- **`gui_loop.sh`**: Added `PYTHON=""` variable that stores the detected
  Python interpreter name (`python3` or `python`). NWG test section now
  uses `$PYTHON` instead of hardcoded `python3`.
- **`gui_loop.sh`**: Added `HAS_WSL_CARGO` check that probes `cargo`
  availability inside WSL via `wsl.exe bash -c "command -v cargo"`.
  GTK test section now uses `HAS_WSL_CARGO` instead of `HAS_CARGO`.
  When WSL has no Rust toolchain, GTK tests are properly SKIPped with
  "cargo not installed in WSL" instead of reporting FAIL.
- **`gui_loop.sh`**: Consolidated GTK3/GTK4 into a single build step
  (the same binary supports both at runtime via `GTK_DLOPEN_PREFER_GTK3`).
